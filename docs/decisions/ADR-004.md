# ADR-004 — Clinical applications are discovered through the DI container, not by scanning assemblies

## Context

FR-502 says applications "shall be discovered through the DI container at startup". The
obvious alternative, and the one most plugin systems reach for, is scanning: look in a
`plugins/` folder, load every assembly, reflect over it for types implementing
`IClinicalApplication`, instantiate them. That is what makes a plugin system feel like a
plugin system — a third party drops a DLL in a folder and their tool appears in the menu,
with no rebuild.

It is worth being honest that scanning is the more impressive-looking answer, and it is
what someone might expect to see in a project whose stated point is a pluggable clinical
platform. Choosing against it needs a reason better than "the requirement said so".

## Decision

Registration is an explicit line in the composition root:

```csharp
services.AddSingleton<IClinicalApplication, HistogramApplication>();
```

The container hands `MainViewModel` an `IEnumerable<IClinicalApplication>`. Nothing
reflects, nothing enumerates a directory, nothing loads an assembly that was not referenced
at build time. Adding Phase 2's calcium scoring application is one more line here.

## Consequences

**What is available is what someone wrote down.** The list of applications a viewer can run
is a line of source in a file under review, in version control, attributable to a commit.
With scanning, the answer to "what can this build run?" depends on the contents of a folder
on the machine it is running on, which is not a question source control can answer.

**An application cannot appear because a DLL was in a folder.** In software that displays
medical images, code arriving into the process by discovery rather than by decision is a
supply-chain problem wearing an extensibility costume. Scanning also means loading and
reflecting over assemblies before anything has decided they are trustworthy.

**Failure is a compile error rather than a silent absence.** A misnamed or moved plugin type
does not build. With scanning, a plugin that fails to load is at best a log line nobody
reads and at worst an application that quietly is not in the menu.

**No hot-loading and no third-party plugins without a rebuild.** This is the real cost.
Anyone wanting to add an application must have the source and rebuild the shell. For a
first-party platform where the applications ship with the viewer — which is what both
phases describe — that is not a cost anyone pays. If the product ever needed genuine
third-party extensibility, this decision would have to be revisited, and it would arrive
with the signing, versioning and isolation questions that scanning quietly skips today.

**The seam is unaffected.** Discovery and contract are separate concerns: `IClinicalApplication`
knows nothing about how its implementations were found, so replacing this with scanning
later changes one file and no interface.
